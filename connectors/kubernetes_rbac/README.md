# Kubernetes Offline RBAC Reference Profile

Status: synthetic, read-only normalization experiment; no Kubernetes client, kubeconfig read, API request, authentication or cluster mutation. Apache-2.0 code; original profile/fixture definition CC-BY-4.0. This is not full Kubernetes or managed-cluster conformance.

## Finite Profile

Input is a closed JSON bundle with metadata, metadata-only ServiceAccount objects, Role/ClusterRole objects and RoleBinding/ClusterRoleBinding objects. Namespaces and valid API-audience unexpired token metadata must be explicitly declared. A ServiceAccount object alone does not invent an issued token. Built-in service-account/all-authenticated group membership is represented; external users/groups and system:masters are not silently guessed.

The universe is one collection/action for each declared namespace and each of pods, configmaps and secrets: read for pods/configmaps, read_secret for secrets. All are included even when ungranted. This read-only universe is not comparable to a full cluster action catalog or to a bucket/object inventory from another platform. Secrets sensitivity1 and other collections0.5 are explicit reference-profile assumptions, not observed data classifications.

get/list/watch are collapsed into existential read capability. Crucially, list/watch on Secrets can disclose values, so they map to read_secret, NOT read_metadata. No Secret object or data/stringData field is imported. Optional stored_credentials sidecars state which already-declared credential metadata is obtainable in a namespace's Secret collection; read_secret remains a mandatory prerequisite and acquisition costs one step. This does not infer that every modern service-account token is stored as a Secret.

RoleBindings are namespace-scoped even when referring to a ClusterRole. ClusterRoleBindings apply to the finite inventory of all declared namespaces. Cross-namespace ServiceAccount subjects are supported when explicitly named. Roles are additive; no fictional deny rule is inserted.

Rejected: extra/unrecognized fields; resourceNames; wildcards; nonresource URLs; aggregated ClusterRoles; unsupported API groups/resources/subresources; create/update/patch/delete; workload creation; impersonation; bind/escalate; token requests; certificate issuance; system:masters; unknown authorizers or token context. Workload creation can imply access to mounted secrets and other service accounts, so mapping it as an ordinary write would understate reach. A separate reviewed profile is required.

## Verified Documentation

- [Kubernetes RBAC authorization](https://kubernetes.io/docs/reference/access-authn-authz/rbac/): RoleBinding/ClusterRoleBinding scope, additive rules, built-in subjects and aggregated roles.
- [Service accounts](https://kubernetes.io/docs/concepts/security/service-accounts/): namespaced workload identities; token validity/audience and modern projected versus legacy stored tokens.
- [RBAC good practices](https://kubernetes.io/docs/concepts/security/rbac-good-practices/): Secret list/watch disclosure, workload-creation privilege, impersonation/escalation and system:masters bypass.
